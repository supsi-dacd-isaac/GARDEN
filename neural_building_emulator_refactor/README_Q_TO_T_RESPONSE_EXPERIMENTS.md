# Fast Qroom-to-Tin Response Experiment

This study separates the heating-block error from the thermal-response error before paying for another global probabilistic run. It uses the **saved calibrated-four-model benchmark split** and does not select a model on its untouched test buildings.

The runner is `q_to_t_response_experiments.py`. **Each command runs exactly one step** and writes its result under a separate directory. The frozen cohort and completed artifacts are reused on later invocations; `--rerun` explicitly repeats a completed step.

```bash
.venv/bin/python -m neural_building_emulator_refactor.q_to_t_response_experiments --step 1
.venv/bin/python -m neural_building_emulator_refactor.q_to_t_response_experiments --step 2
.venv/bin/python -m neural_building_emulator_refactor.q_to_t_response_experiments --step 3
```

All three commands use the same `--benchmark-dir` and `--output-dir`. Run them in order. The default pilot randomly freezes 100 benchmark training buildings and 12 benchmark validation buildings with `--seed 13`; stage 2 scores six validation buildings for each of two fitting seeds. Change `--train-profiles`, `--validation-profiles`, or the benchmark path **before step 1**, or use a new output directory for a different cohort.

## Step 1: Observed-Q Thermal Oracle

Load the existing probabilistic structured checkpoint. On six validation profiles, replay the same particle keys twice, with expected HP power and EnergyPlus-rule ventilation. The second replay substitutes **observed Qroom[t] only where Q enters the thermal forcing and positive leaky heat-response bank**. The emitted Qroom and Pel predictions are still generated by the HP block.

Compare annual Tin RMSE and 0.5/1-hour pre/post Tin response RMSE. A large oracle improvement implicates the heating/hydronic block; little improvement or deterioration implicates the thermal response or closed-loop coupling. This is an isolation diagnostic, **not** an autonomous forecast: changed Tin feeds back into the HP block, so Q/P scores from the oracle replay are not interpretable as a new model's performance.

Outputs: `step1_oracle/profile_metrics.csv`, `summary.json`, `oracle_dashboard.html`.

## Step 2: Deterministic Three-Arm Ablation

Fit these arms from scratch on the **identical frozen cohort**, using the calibrated benchmark's deterministic architecture, optimizer, state dimensions, Q-to-T time constants, area scaling, and HP controller. Only the temperature-update rule changes:

| Arm | Update | Purpose |
| --- | --- | --- |
| `A_leaky_2c` | Existing leaky equilibrium, 2 C nominal step bound | Control |
| `B_leaky_3c_diagnostic` | Same rule, 3 C nominal step bound | Test whether the alpha ceiling is the bottleneck; not a final candidate |
| `C_alpha_bounded_2c` | Learned building-specific alpha, tanh-bounded 2 C update | Candidate with faster response and a hard step cap |

The C alpha head starts near 0.1 rather than near 0.5. Its alpha is learned thereafter. Both seeds use exactly the same training and validation IDs. The script scores full-year Tin/Q/P RMSE, Tin RMSE while space heating is available/unavailable, Tin response RMSE and signed response gain per kelvin over 0.5 and 1 hour, response error where Q changes match within 5 W/m2, and the stricter subset where observed Q also changes by at least 5 W/m2. It also records maximum Tin step, raw gradient norm, and skipped updates.

C is promoted only if its mean 0.5-hour Tin response RMSE improves at least 10%, annual Tin RMSE worsens at most 5%, Q/P RMSE each worsen at most 10%, and it causes no more skipped updates than A. These are **pilot thresholds**, not a claim that every building improves. B cannot be promoted because it relaxes the desired step cap.

Outputs: `step2_deterministic/{arm}/seed_{seed}/` checkpoints, `validation_profile_metrics.csv`, `summary.json`, `deterministic_dashboard.html`. Per-epoch gradient diagnostics remain with each artifact.

## Step 3: Matched Probabilistic Replication

If C passes step 2, fit **both A and C probabilistically** on that same frozen train/validation cohort. This is a matched control, not a comparison against the old 1000-building checkpoint. The small pilot defaults to eight training/evaluation particles, six epochs, and 16 annual scoring scenarios; increase those counts for a final calibration claim. The script scores the same response/annual metrics, scenario response coverage, and the untouched benchmark test buildings **only after** promotion.

If C fails, step 3 prints why it was skipped and trains nothing.

Outputs: `step3_probabilistic/{arm}/` checkpoints, `profile_metrics.csv`, `summary.json`, `probabilistic_dashboard.html`.

## Step 4: Capped-Alpha Follow-Up

After step 3, cap C's rollout-constant alpha while retaining the same 2 C hard temperature-step bound. This follow-up trains only capped C and reuses the completed A and uncapped-C scores, so the earlier artifacts are not overwritten:

```bash
.venv/bin/python -m neural_building_emulator_refactor.q_to_t_response_experiments \
  --step 4 \
  --alpha-cap 0.5 \
  --prob-epochs 8 \
  --prob-particles 8 \
  --prob-eval-particles 8 \
  --prob-score-scenarios 32
```

The output is written under `step4_alpha_cap_0p5/`. The cap is structural:

```text
alpha = alpha_cap * sigmoid(raw_alpha)
```

The output-layer bias is adjusted so every cap starts near `alpha=0.1`; therefore this comparison does not accidentally halve C's initial response merely by changing the cap.

## Step 5: Fixed-Alpha Isolation

Remove the alpha network and repeat C with one fixed trajectory-wide value. This
isolates learned alpha and its parameter-gradient path while retaining C's
bounded-tanh update, dynamic transition, HP model, and all training losses:

```bash
.venv/bin/python -m neural_building_emulator_refactor.q_to_t_response_experiments \
  --step 5 \
  --alpha-cap 0.5 \
  --fixed-alpha 0.05 \
  --prob-epochs 8 \
  --prob-particles 8 \
  --prob-eval-particles 8 \
  --prob-score-scenarios 32
```

Step 5 requires the matching step-4 output and writes to
`step5_fixed_alpha_0p05/`. With fixed alpha enabled,
`temperature_alpha_net` is structurally absent and its reported gradient norm
must be exactly zero.

## Step 6: Metadata-Conditioned Alpha

Restore learned building-specific alpha but remove its dependence on the
persistent particle latent variable `xi`:

```bash
.venv/bin/python -m neural_building_emulator_refactor.q_to_t_response_experiments \
  --step 6 \
  --alpha-cap 0.5 \
  --prob-epochs 8 \
  --prob-particles 8 \
  --prob-eval-particles 8 \
  --prob-score-scenarios 32
```

Here `alpha = alpha_cap * sigmoid(alpha_net(metadata))`. Alpha can vary between
buildings but is identical across every particle of one building. All other
uses of `xi` remain unchanged. Step 6 requires the matching step-4 output and
writes to `step6_metadata_alpha/`.

## Interpretation

The primary question is whether the current equilibrium alpha limit is slowing Tin despite adequate Q. Step 1 tests the adequacy of the thermal path with observed heat; step 2 tests alpha-related alternatives cheaply; step 3 checks whether a deterministic response win survives scenario sampling. The annual Tin fit and raw gradients are guardrails because a faster local response is not useful if it destabilizes longer rollouts.
